## 2024-05-18 - Replacing O(N) list scans with O(1) derived map lookups
**Learning:** During UI rebuilds, `LibraryPage` was previously performing an $O(N)$ linear scan on `playlistsProvider` on every widget rebuild via `playlists.where((p) => p.id == id).firstOrNull`. While raw Dart iteration is fast for small lists, caching a derived $O(1)$ lookup map using Riverpod `Provider` (e.g., `playlistsByIdProvider`) creates a scalable, clean solution that avoids overhead during frequent UI events.
**Action:** When finding `.where(...).firstOrNull` style lookups inside a Flutter `build()` method backed by a Riverpod `StreamProvider` or list provider, extract the map calculation to a new derived `Provider` that returns a `Map<K, V>`. This ensures the map is only reconstructed when the underlying list actually emits new data, replacing O(N) widget rebuilds with O(1) lookups.
## 2024-05-18 - Fast Text Search with Null-Byte Concatenation
**Learning:** When implementing text search functionality across multiple fields (like title, artist, album, genre) in Dart, generating a `List<String>` of fields per object and iterating it via `.any((field) => field.contains(needle))` introduces a lot of memory overhead from list and closure allocations. Pre-computing a single concatenated string delimited by null bytes (`\u0000`) and searching it with `.contains(needle)` avoids these allocations and runs significantly faster in tight loops.
**Action:** When searching across multiple string properties for objects in memory, join the fields with a null byte (`'\u0000'`) and perform a single `.contains()` check on the concatenated string instead of allocating lists and iterating with `.any()`.
## 2024-05-18 - Avoid putIfAbsent inside tight O(N) loops in Dart
**Learning:** In Dart, calling `putIfAbsent` inside a loop is problematic because it requires a callback function, forcing an anonymous closure allocation (e.g., `() => []`) on every single iteration, even if the key is already present. This increases memory churn and garbage collection pressure when processing large collections, like the tens of thousands of tracks during audio library indexing.
**Action:** Replace `map.putIfAbsent(key, () => value)` with the null-aware assignment operator `map[key] ??= value`. Because `??=` short-circuits, it only evaluates the right-hand side if the key is absent/null, bypassing the closure allocation entirely.
## 2024-05-18 - Batch inserting Subsonic tracks avoids N+1 queries
**Learning:** Inserting tracks into the Drift database one by one inside a loop using `getOrInsertTrack` causes a massive N+1 query overhead. Processing 1,000 tracks dropped from ~319-893ms down to ~66-82ms by using Drift's `batch` insertion (`upsertTracks`) combined with an `isIn` query to fetch the generated IDs in chunks (to respect SQLite limits).
**Action:** When inserting large lists of dynamic dependencies or remote data that must be mirrored to the database (like importing a remote playlist), always collect the companions and use `batch()` or a transaction, followed by chunked sequential selects, instead of looping single inserts.
## 2024-05-18 - Replacing putIfAbsent with null-aware assignment ??= in loops
**Learning:** In Dart, calling `putIfAbsent` requires passing a closure (e.g., `() => value`). When used inside a tight loop (such as iterating over tens of thousands of tracks during indexing), this allocates an anonymous closure function on the heap for every single iteration, even if the key already exists. This introduces unnecessary memory churn and Garbage Collection overhead.
**Action:** Replace `map.putIfAbsent(key, () => value)` with the null-aware assignment operator `map[key] ??= value`. This short-circuits the evaluation and avoids the closure allocation entirely.
## 2024-05-18 - Optimize TextField Rebuilds with ValueListenableBuilder
**Learning:** In Flutter applications, hooking up a `TextEditingController` to `setState` via the `onChanged` callback of a `TextField` causes the entire parent widget to rebuild on every single keystroke. When this state is only used to enable or disable a specific localized UI element (like a 'Save' or 'Submit' button), triggering a full widget rebuild is highly inefficient.
**Action:** Remove `onChanged: (_) => setState(() {})` from the `TextField` and instead wrap the specific dependent widget (e.g., the Submit `TextButton`) with a `ValueListenableBuilder<TextEditingValue>` that listens to the `TextEditingController`. This isolates the rebuild to just the button, dramatically improving typing responsiveness and preventing unintended re-evaluations of expensive operations within the parent widget's build method.
